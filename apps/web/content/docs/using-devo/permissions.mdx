---
title: Permissions
description: Review and control tool execution.
---

Permissions control what tools Devo can run without asking and what must be
approved first.

New sessions default to **Full Access** with the shell sandbox **off** when no
explicit configuration applies. This skips approval prompts and allows tools to
use the current user's filesystem and network access. It does not grant root or
administrator privileges. Use this default only with trusted workspaces and tasks.

The Desktop permission picker and TUI `/permissions` command are currently hidden.
Explicit project permissions and sandbox profiles remain supported through config
and the Native `session/metadata/update` API. Desktop new chats inherit the server's
resolved settings rather than overwriting project configuration with a hidden picker value.

## Presets and sandbox profiles

| Preset | Without Approval | Approval Behavior | Implied Shell Sandbox |
| --- | --- | --- | --- |
| Default | Read/edit workspace files and eligible workspace shell commands. | Sensitive requests ask the user. | `workspace` |
| Auto-review | Same base policy as Default. | Eligible requests go to the reviewer; uncertain or failed reviews ask the user. | `workspace` |
| Full Access | Tool requests are allowed under the full-access policy. | No approval prompts. | `off` |

Approval policy and OS sandboxing are separate controls. For new sessions,
`projects.<path>.permission_preset` overrides the Full Access default. The sandbox
is selected from the project `sandbox_profile`, then `[permission].sandbox_profile`,
then the preset's implied profile. Thus Full Access can coexist with an explicitly
configured sandbox. The `workspace` profile restricts filesystem writes but does
not itself block network access; network approval is a separate policy layer.

`read-only` is a sandbox profile, not a permission preset. A legacy `read-only`
preset maps to `default`, which permits shell commands.

Saved session settings are restored rather than replaced with new-session
defaults. Changing a session's permission preset re-derives its sandbox; an
explicit `sandboxProfile` in the same settings patch takes precedence.

## Non-interactive prompts

`devo prompt` shares the same new-session defaults and honors project/global
sandbox overrides. It has no interactive approval controller. If a project
explicitly selects `default` or `auto-review`, the command exits before provider
initialization or tool execution with an error instead of silently bypassing that
policy. Use interactive `devo` for those projects. Existing unconfigured headless
workflows continue with Full Access and no OS shell sandbox. Invalid configuration
also fails instead of falling back to permissive defaults.

## Approval Prompts

When Devo needs approval, the bottom pane opens a prompt titled:

```text
Permission approval required
```

The prompt includes the action summary and may include:

- reason;
- resource;
- path;
- host;
- target.

Use the shown options to respond:

| Option | Shortcut | Effect |
| --- | --- | --- |
| Yes, proceed | `y` | Allow only this pending tool execution. |
| Don't ask again for this command in this session | `s` | Allow matching requests for the rest of this session, when the request supports session scope. |
| Don't ask again for commands that start with a prefix | `p` | Save a persistent allow rule for that command prefix, when offered. |
| Don't ask again for files under a path | `f` | Allow matching path prefixes for the rest of this session, when offered. |
| Allow this host for this session | `h` | Allow the requested network host for the rest of this session, when offered. |
| No, continue without running it | `n` | Reject this tool execution and let the agent continue. |

`Esc` cancels the approval request and interrupts the turn.

If a sandboxed shell command is denied by the OS sandbox after a Tier 1
`with_additional_permissions` approval, Devo keeps the command sandboxed and
returns the denial so the model can request the missing capability. Tier 1
approval never silently turns into full access. Only an approved
`require_escalated` request runs without the sandbox.

## Auto-review

The `Auto-review` preset uses the same base permissions as `Default`, but
approval requests that are eligible for review are first sent to Devo's
automatic approval reviewer. This includes both `require_escalated` and
`with_additional_permissions` requests; the reviewer sees the requested tier
and exact additional paths/network access.

The reviewer can:

- approve clearly low-risk actions scoped to the stated target;
- deny destructive, credential-related, privilege-escalating, or ambiguous
  high-impact actions;
- return uncertain when user intent or risk is unclear.

Uncertain requests are still shown to you. Reviewer timeouts, provider
failures, and invalid output are also sent to you after one bounded retry for
transient failures. Auto-review is a filter before user interruption, not a
replacement for your judgment.

## Review Habits

Before approving, check the resource and target:

- For file edits, confirm the path is inside the intended workspace.
- For shell commands, read the exact command target.
- For network access, confirm the host is expected.
- For broad session approvals, make sure future matching requests would still
  be safe.

If the request is surprising, deny it and ask Devo to explain or choose a
narrower action.

## Project Permission Memory

When you change permissions, Devo records the selected preset for the active
project in user config. That lets future sessions for the same project start
with the expected policy instead of asking you to reselect it every time.
