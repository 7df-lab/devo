---
title: Context and Compaction
description: Understand how Devo manages long-running context.
---

Every Devo turn sends a context package to the selected model. That package can
include instructions, workspace context, available skills, active goal state,
conversation history, tool results, and the latest user message.

The selected model's context window limits how much can fit.

## Context Window

Model profiles include a context window and, when configured, an effective
usable percentage. Devo uses those values to estimate how full the current
session is and when compaction may be needed.

The TUI can show token usage, context-window size, and context pressure in the
status surfaces. These numbers are estimates, but they are useful for spotting a
session that is getting large.

## What Gets Sent

Devo builds context from multiple sources:

- runtime and developer instructions;
- discovered project instructions;
- active skill information;
- memory and goal context when applicable;
- conversation history;
- tool-call and tool-result records;
- the current user turn.

## Automatic Compaction

A single user turn can contain many model calls. Before sending the next call,
Devo checks the assembled input estimate, the requested output allowance for
the active API, and the latest reported usage. A large tool result can trigger
a checkpoint even when the preceding model response reported little usage.

Automatic checkpoints preserve the current task's original user input and its mid-turn human corrections verbatim. Completed work, including
tool arguments and results from the current turn, can enter the summary. Devo
normally keeps a recent tail of up to one quarter of the configured input
budget, capped at 20,000 estimated tokens. It cuts at the end of a complete
tool batch. An unfinished batch stays together, including results already
received for parallel calls.

Devo replaces the selected model history with one checkpoint. The next model
call continues the same turn with that checkpoint and the preserved items.
Later checkpoints incorporate the previous one. The original conversation and
tool records remain available in the transcript.

In a persistent session the model can use `await rlm.history.search('error text', kind='tool_result')` and `await rlm.history.read(item_id, offset=offset)` to recover recorded evidence from the active branch. A checkpoint includes up to six tool references. Reads are paged, include completed work from the running turn, and follow branch navigation.

## Manual Compaction

Use `/compact` when you want to compact the current session proactively.

The command operates on the current model-facing history while the session is
idle. During an active turn, Devo can checkpoint automatically between model
calls.

The TUI reports compaction lifecycle events:

- compaction started;
- compaction completed;
- compaction failed.

## Failure And Retry

If the provider still rejects the rebuilt request, Devo can summarize the
remaining completed work and retry. Automatic recovery only installs a
checkpoint that reduces estimated history size. The original user input,
unfinished tool calls and fixed instructions can still exceed a provider limit.

If the summarizer's request is too large, Devo splits the selected history
into ordered fragments and carries each partial summary into the next. A single
large text result can span several fragments. Only a completed checkpoint
replaces history. Cancellation, an indivisible input, or exhaustion of the
bounded recovery attempts leaves the last committed checkpoint available.

## Practical Guidance

Use `/compact` after a large investigation before asking Devo to implement a
change. Use `/goal` when the larger objective should remain explicit across
compaction or resumed turns.

When a session is important, make key decisions explicit in normal chat before
compaction. Summaries preserve intent best when the transcript contains clear
decisions and constraints.
