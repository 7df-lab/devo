title: Models and Provider Connections
description: Understand provider templates, Connections, models, and variants.
---

Devo has two model data sources: the live models.dev directory and user
configuration. Public provider endpoints and model metadata are fetched into
server memory, never bundled or persisted as catalog snapshots. Configured
Connections pin endpoint, protocol and model IDs in user/workspace
`providers.json`; credentials remain in user-scoped `auth.json`.

Refresh failures keep the same process's last successful directory and all
configured models. A fresh offline start has no public directory. Provider
Discover is read-only: save selected suggestions explicitly to configure them.
Older sparse connections without pinned endpoints must be reconnected explicitly.
Existing configuration files are preserved; old snapshots are ignored, not deleted.

## TUI setup

`/model` opens in All mode, showing configured models, supported public models
from models.dev (including providers you haven't signed in to), and models
discovered for signed-in subscriptions. The public catalog and connected OAuth
providers' model lists load in the background when needed. After restarting Devo,
`/model` can rediscover models using your saved OAuth connection without requiring
another sign-in. If you've saved a model scope, use **Alt+S** to switch to it.
Choose a public API-key model to sign in and save its Connection. Devo saves the
provider endpoint and protocol on explicit login, then saves the selected model's
route without copying the rest of the public catalog. An existing custom endpoint
is not replaced.

Use `/login` or press **Ctrl+L** in the default `/model` picker to open Providers.
OpenAI Codex subscription models are discovered after ChatGPT OAuth; they are
not the OpenAI API-key models in the public catalog. Devo saves the selected
subscription model and its advertised effort settings. Sign in again and
reselect a previously saved subscription model if its effort picker is missing.

`/effort` uses the levels advertised by the selected provider: models.dev for
public API-key models when it specifies effort options, and authenticated model
discovery for Codex subscription models.

## Provider and model identity

Provider ids and nested model ids are map keys. The optional `request_model` field overrides the upstream request ID without
changing the stable selection identity:

```json
{
  "model": "deepseek/deepseek-v4-flash",
  "provider": {
    "deepseek": {
      "base_url": "https://api.deepseek.com/anthropic",
      "credential": "deepseek_api_key",
      "wire_api": "anthropic_messages",
      "models": {
        "deepseek-v4-flash": {
          "name": "DeepSeek V4 Flash",
          "context_window": 200000
        }
      }
    }
  }
}
```

The nested key is the second half of `provider/model` and defaults to the upstream
request ID. Model-level `base_url` and `wire_api` can pin a route independently
of provider defaults. `name` is only a display label.

## Model metadata

Model records can describe context limits, output limits, input modalities,
reasoning controls, sampling defaults, capabilities, cost, release status,
arbitrary request/options/headers, and named variants. The common onboarding
form exposes the useful fields first; Advanced settings exposes the rest.

`small_model` is an optional root selection for lightweight background work,
such as session-title generation. When absent or invalid, Devo chooses a
recognizably lightweight model from the primary provider and then falls back to
`model`.

## Wire APIs

The selected model uses one of these request protocols:

| Wire API | Meaning |
| --- | --- |
| `openai_chat_completions` | OpenAI-compatible Chat Completions API. |
| `openai_responses` | OpenAI-compatible Responses API. |
| `anthropic_messages` | Anthropic-compatible Messages API. |

DeepSeek's official Anthropic-compatible endpoint is represented by a normal
Connection whose `wire_api` is `anthropic_messages`.

## Reasoning and variants

`reasoning_capability` controls the values shown in the picker. A model variant
is selected with `provider/model/variant`; it is not another model identity.
Variant request fields, options, and headers are layered after the model and
provider values. This supports OpenCode-style fast/reasoning variants without
duplicating provider or model records.

## Resolution

For a turn, Devo resolves the explicit `provider/model[/variant]` reference,
checks that the Connection and model are enabled, resolves the credential from
`auth.json`, merges request defaults, and sends the request through the model's
wire API. `/model` and the CLI `--model` use the same reference format.

If no Connection is configured, run:

```bash
devo onboard
```
