Devo 的模型数据只有两类：实时 models.dev 目录和用户配置。公共 provider endpoint 和模型
元数据只保存在服务端内存中，不内置目录，也不保存磁盘快照。用户配置的 Connection 在
用户/工作区 `providers.json` 中固定 endpoint、协议和 model ID；凭据仍保存在用户级 `auth.json`。

刷新失败会保留本进程最近一次成功的目录和全部用户配置模型。首次离线启动没有公共目录。
Provider Discover 只返回临时建议，不会写入配置；需要显式保存选中的模型。
旧的稀疏连接若没有固定 endpoint，需要显式重新连接。现有配置文件保留，旧快照忽略但不删除。

## Provider 和 Model 身份

Provider id 和嵌套 model id 都是 map key。可选的 `request_model` 字段可以覆盖上游请求 ID，不改变稳定的选择身份：

```json
{
  "model": "deepseek/deepseek-v4-flash",
  "provider": {
    "deepseek": {
      "base_url": "https://api.deepseek.com/anthropic",
      "credential": "deepseek_api_key",
      "wire_api": "anthropic_messages",
      "models": {
        "deepseek-v4-flash": {
          "name": "DeepSeek V4 Flash",
          "context_window": 200000
        }
      }
    }
  }
}
```

嵌套 model key 是 `provider/model` 引用的后半部分，默认也是上游请求 ID。模型级
`base_url` 和 `wire_api` 可以独立固定路由；`name` 仅用于显示。

## Model 元数据

Model record 可以描述上下文长度、输出上限、输入模态、reasoning 控制、采样默认值、能力、
价格、发布状态、任意 request/options/headers 和命名 variants。Onboarding 常用表单会先显示
常用字段，高级设置显示其余字段。

根字段 `small_model` 是可选的轻量后台模型选择，例如用于生成 session 标题。它缺失或无效时，
Devo 会先从主模型所在 provider 中选择明显轻量的模型，最后回退到 `model`。

## Wire API

选中的模型使用以下请求协议之一：

| Wire API | 含义 |
| --- | --- |
| `openai_chat_completions` | OpenAI 兼容 Chat Completions API。 |
| `openai_responses` | OpenAI 兼容 Responses API。 |
| `anthropic_messages` | Anthropic 兼容 Messages API。 |

DeepSeek 官方 Anthropic-compatible endpoint 表示为普通 Connection，其 `wire_api` 为
`anthropic_messages`。

## Reasoning 和 Variants

`reasoning_capability` 决定 picker 展示哪些值。通过 `provider/model/variant` 选择模型 variant；
variant 不是另一种模型身份。Variant 的 request、options 和 headers 会在 model/provider 值之后
合并，因此可以支持 OpenCode 风格的 fast/reasoning variants，而不需要复制 provider 或 model。

## 解析

每个 turn 都会解析明确的 `provider/model[/variant]` 引用，检查 Connection 和 model 已启用，
从 `auth.json` 解析 credential，合并请求默认值，再通过模型的 wire API 发送请求。`/model` 和
CLI `--model` 使用同一种引用格式。

如果尚未配置 Connection，请运行：

```bash
devo onboard
```
